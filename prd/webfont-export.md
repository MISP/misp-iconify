# Feature — Webfont export (`.woff2` + `icons-font.css`) for FontAwesome-style consumption

**Status:** Phases 1–2 implemented — `make font` builds the font for
hexagone/simple/attributes/objects-framed (Phase 1, 2026-07-01) plus objects and
galaxies (Phase 2, 2026-07-02): 639 glyphs. Only Phase 3 (galaxies-orbit) pending.
**Owner:** Sami Mokaddem
**Created:** 2026-07-01
**Area:** `src/scripts/`, `Makefile`, `exports/font/` (new), `metadata/`, `.github/workflows/generate-assets.yml`
**Motivation:** Integrating misp-iconify into consumers that render icons as **text/SVG `<text>`** (e.g. Pivotick graph nodes) — the current mask-only export cannot be used there.

---

## 1. Background

Today misp-iconify ships icons in three rasterisable/mask forms, all generated by
`make all` from `src/svg/<variant>/<name>.svg`:

- `exports/css/icons.css` — one class per `(name, variant)`, each a base64
  `mask-image` data URI painted with `background-color: currentColor`
  (`src/scripts/generate-css.sh`).
- `exports/png/{1x..5x}` and `exports/webp/**` — rasterised bitmaps.

The mask approach is versatile but has one structural limitation: **a CSS mask
needs a filled HTML box to cut into.** It works on a `<span>`, `<i>`, `<div>` —
anything with `width`/`height` and `background-color`. It does **not** work on an
SVG `<text>` element, because text has no background box for the mask to reveal.

FontAwesome-style icon libraries do not use masks — they are **webfonts**: each
icon is a glyph at a private-use Unicode codepoint, and rendering an icon means
"set `font-family` + emit the codepoint as text." A glyph renders anywhere text
renders, including SVG `<text>`.

### Concrete driver: Pivotick

Pivotick's `iconClass` / `iconUnicode` node hook renders the icon by appending an
SVG `<text>` element and setting its content to a glyph looked up from the CSS
`--fa` custom property (`faGlyph()` in `src/utils/Getters.ts`). Because
misp-iconify is mask-based, this path is unusable, and the MISP "Pivot Explorer"
integration currently has to fall back to Pivotick's heavier `html` hook
(a `<foreignObject>` per node wrapping a `<span class="misp-icon …">`). A webfont
export would let that consumer — and any future one — use the native text path and
drop the `<foreignObject>` entirely.

## 2. Goals

1. Produce a **webfont** (`misp-iconify.woff2`, with `.woff` fallback) containing
   every icon as a monochrome glyph, one glyph per `(name, variant)` pair.
2. Produce an opt-in **`exports/font/icons-font.css`** that:
   - declares the `@font-face`,
   - keeps the **exact same class names** as `icons.css`
     (`.misp-icon`, `.misp-icon-<name>.misp-<variant>`) so consumer markup is
     identical whether they load the mask CSS or the font CSS,
   - exposes each icon's codepoint in the forms a text consumer needs
     (`::before { content }` for HTML, plus a machine-readable custom property).
3. Guarantee **stable codepoints** across rebuilds (checked-in codepoint map).
4. Integrate cleanly into the existing bash + Inkscape + Makefile pipeline and CI.

## 3. Non-goals

- **Not** replacing the mask CSS. Masks remain the default and stay first-class;
  the font is an additional, mutually-exclusive stylesheet the consumer opts into.
- **No multi-colour icons.** A font glyph is single-colour by definition. This is
  acceptable: every source SVG is monochrome (`currentColor` only). Colour-layered
  formats (COLR/CPAL, SVG-in-OpenType) are explicitly out of scope.
- **No ligature support** in v1 (typing `"domain"` → glyph). Optional future work.
- **No change to `src/svg/**` source files.** Outlining happens in the build,
  against copies, so masks/PNG/WebP are unaffected.

---

## 4. The core technical challenge — strokes must be outlined to fills

This is the crux of the feature and the main reason it is not a trivial "run a
font generator over the SVGs" task.

The source glyphs are **stroked**, not filled. Example — `src/svg/attributes/domain.svg`:

```xml
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24">
  <g fill="none" stroke="currentColor" stroke-linecap="round"
     stroke-linejoin="round" stroke-width="2">
    <path d="M3 12a9 9 0 1 0 18 0a9 9 0 0 0-18 0m.6-3h16.8M3.6 15h16.8"/>
    <path d="M11.5 3a17 17 0 0 0 0 18m1-18a17 17 0 0 1 0 18"/>
  </g>
</svg>
```

- **Masks tolerate this**: `mask-image` uses the SVG's *rendered pixel coverage*,
  and a stroked path renders visible pixels. PNG/WebP rasterisation likewise.
- **Fonts do not**: a glyph outline is a set of *filled contours*. A path with
  `fill="none"` contributes **nothing** to a glyph — the icon would come out
  blank. Every stroke (and `stroke-linecap`/`stroke-linejoin`/`stroke-width`)
  must first be converted into an equivalent **filled outline** ("stroke to path"
  / "outline stroke"), preserving round caps/joins.

Additional wrinkles the outliner must handle:

- **Dashed strokes.** `galaxies-orbit` wraps each glyph in a dashed orbital ring
  (`stroke-dasharray="1.7 1.9"`, see `src/scripts/frame-galaxies.sh`). Outlining a
  dashed stroke produces one small filled contour *per dash* — dozens of tiny
  contours per glyph. This bloats the font and looks noisy at text sizes; see
  §8 phasing.
- **Overlapping contours.** After outlining, overlapping sub-paths should be
  unioned (boolean union) so the glyph has clean, non-self-intersecting outlines
  and correct winding, otherwise counters (holes) may fill or drop out.
- **Masked "knockout" icons.** ~40 `file-*` icons plus `x509` (the Tabler idiom)
  paint a `currentColor` box through a `<mask>` whose *white* shapes show and
  *black* shapes hide — the file-type label (`PDF`, `CSV`, …) is a black knockout.
  Outlining ignores masks, so a naive union fills the knockouts and every file-type
  renders identically. These must be resolved to **show − hide**: union the shown
  shapes, then boolean-subtract the black ones, before glyph assembly. (Implemented
  in `generate-font.sh: outline_icon()`.)
- **Em-square mapping.** The variants do not share one `viewBox` (attributes/
  objects-framed are `0 0 24 24`, hexagone `0 0 32 32`, simple a padded ~30-unit
  box). They are all *square*, so mapping each glyph's own viewBox onto the em
  (fantasticon `normalize: true`, `fontHeight: 1000`) reproduces the mask's
  `mask-size: contain` and gives every glyph a consistent visual weight.

## 5. Design

### 5.1 Codepoint allocation & stability

- Assign each `(variant, name)` a codepoint in the Unicode BMP Private Use Area
  (`U+E000`–`U+F8FF`, 6400 slots; 770 glyphs today — ample headroom).
- Persist the mapping in a checked-in **`metadata/codepoints.json`**:

  ```json
  {
    "attributes/domain":      "e001",
    "attributes/ip-src":      "e002",
    "objects-framed/file":    "e1a0",
    "simple/event":           "e300"
  }
  ```

- **Append-only, never reassign.** New icons take the next free codepoint; a
  removed icon's codepoint is retired, not reused. This is the FontAwesome /
  Fontello contract — consumers may hardcode or cache codepoints, so shuffling
  them silently breaks them. The build must read the existing map, assign only
  *new* keys, and fail loudly if a rebuild would change an existing assignment.
- Keys use the same `variant/name` scheme already used in `metadata/icons.json`.

### 5.2 Glyph set

- One glyph per `(variant, name)` — variants are visually distinct, exactly as
  FontAwesome models `fa-solid` vs `fa-regular` as separate glyphs. All seven
  variants in scope: 770 glyphs total (16 hexagone, 16 simple, 50 attributes,
  213 objects, 213 objects-framed, 131 galaxies, 131 galaxies-orbit) — subject to
  the phasing in §8.

### 5.3 Font files

- **`exports/font/misp-iconify.woff2`** — primary (best compression; universal
  modern-browser support).
- **`exports/font/misp-iconify.woff`** — fallback for older engines.
- Font internal family name: **`"MISP Icons"`**.
- Rough size expectation: ~770 monochrome glyphs ≈ 100–250 KB woff2. Acceptable;
  note it is a single request vs. the ~3.8 MB inlined mask CSS.

### 5.4 CSS output — `exports/font/icons-font.css`

Self-contained and **loaded instead of** `icons.css` (see §5.6). Same class names
as the mask CSS so markup is portable:

```css
@font-face {
  font-family: "MISP Icons";
  src: url("misp-iconify.woff2") format("woff2"),
       url("misp-iconify.woff")  format("woff");
  font-display: block;
}

/* Base class — mirrors icons.css but sets the font instead of mask props */
.misp-icon {
  font-family: "MISP Icons";
  font-style: normal;
  font-weight: normal;
  line-height: 1;
  display: inline-block;
  vertical-align: middle;
  -webkit-font-smoothing: antialiased;
  -moz-osx-font-smoothing: grayscale;
}
.misp-fw { width: 1.25em; text-align: center; }

/* Per-icon: expose the codepoint three ways */
.misp-icon-domain.misp-attributes::before { content: "\e001"; }
.misp-icon-domain.misp-attributes {
  --misp-icon: "\e001";   /* canonical machine-readable property */
  --fa: "\e001";          /* alias — zero-change Pivotick faGlyph() compat */
}
```

Rationale for exposing the codepoint three ways:

- `::before { content }` — the normal HTML usage (`<span class="misp-icon …">`).
- `--misp-icon` — the canonical property a JS consumer should read.
- `--fa` — a compatibility alias so Pivotick's current `faGlyph()`
  (which reads `--fa` by name) works with **no change to Pivotick**. This coupling
  is a deliberate shim; the cleaner long-term path is for Pivotick to read a
  neutral property or be handed the codepoint via `iconUnicode` (tracked as an
  upstream Pivotick change, not a blocker here).

The icon is tinted by CSS `color` (not `background-color`) and sized by
`font-size`, exactly like FontAwesome.

### 5.5 Accessibility

Document the FA-style convention in the README: decorative icons get
`aria-hidden="true"`; meaningful icons need an adjacent visually-hidden label or
`role="img"` + `aria-label`. The generated CSS uses `::before` so the glyph is not
part of the accessible text tree by default.

### 5.6 Coexistence with the mask CSS

`icons.css` (mask) and `icons-font.css` (font) define the **same class names** with
conflicting mechanics (`background-color` + `mask-image` vs `font-family` +
`content`). They are therefore **mutually exclusive** — a consumer loads exactly
one. This keeps consumer markup identical while letting them pick the rendering
that fits their context:

| Consumer context | Load |
|---|---|
| HTML boxes, needs `misp-fw`, broad compat | `icons.css` (mask) — default |
| Rendering into text / SVG `<text>` (e.g. Pivotick nodes) | `icons-font.css` (font) |

*(Open decision D-1 in §11: keep identical class names + mutual exclusivity, vs.
namespacing the font classes so both can load together.)*

## 6. Build pipeline & Makefile integration

Add a `font` target and fold it into `all`, after the framing steps (so it
outlines the already content-cropped, framed glyphs) and alongside the other
export generators:

```makefile
all: clean validate optimize fit-ratio frame-objects frame-galaxies \
     metadata catalog attribution png webp css font

font:
	@bash src/scripts/generate-font.sh
```

New script **`src/scripts/generate-font.sh`**, staged so nothing touches
`src/svg/**`:

1. **Copy** in-scope `src/svg/<variant>/<name>.svg` into a scratch build dir.
2. **Outline strokes → fills** on each copy (round caps/joins preserved), then
   **boolean-union** overlapping contours. (Tooling in §7.)
3. **Load/extend `metadata/codepoints.json`**: assign codepoints to any new
   `(variant, name)` keys; abort if an existing assignment would change.
4. **Assemble** `misp-iconify.woff2` + `.woff`, mapping each outlined glyph to its
   codepoint on a normalised em square/baseline.
5. **Emit `exports/font/icons-font.css`** from the codepoint map (§5.4).

### CI

`.github/workflows/generate-assets.yml` installs `imagemagick librsvg2-bin
inkscape libxml2-utils`, sets up Node and runs `npm ci` (for `fantasticon`), then
runs `make assets` followed by `make font`, and commits `exports/` plus
`metadata/codepoints.json`. (Resolves D-2.)

## 7. Tooling options

The repo is intentionally bash + Inkscape + ImageMagick, **no Node**. Two
constraints: (a) outline strokes to fills, (b) assemble glyphs → font + codepoints.

**Recommended (stays in the current toolchain):**

- **Inkscape** (already a dependency) for step 2: it can outline strokes via its
  actions/CLI (Path → Stroke to Path) and union paths. Already used by
  `optimize-svgs.sh`, so no new dependency.
- **FontForge** for steps 3–5: scriptable head-lessly (`fontforge -script …` /
  its Python API), imports SVG outlines, sets codepoints, and exports woff2/woff.
  Pure CLI, apt-installable in CI, no Node.

**Node-based alternatives** (simpler, richer, but add a Node toolchain to a
Node-free repo — a real cost to weigh):

- `fantasticon` — takes an explicit `codepoints.json` (great for §5.1 stability),
  emits woff2/woff + CSS in one pass. *Does not outline strokes* — still needs the
  Inkscape step first.
- `svgtofont` — similar; same stroke caveat.

Recommendation: **Inkscape (outline) + FontForge (assemble)** to preserve the
Node-free pipeline, unless the team already wants a Node dependency for other
reasons.

**Decision (implemented): Inkscape (outline) + `fantasticon` (assemble).** The team
accepted a build-only Node dependency in exchange for a purpose-built icon-font
generator: `fantasticon` takes an explicit codepoints map (directly satisfying the
§5.1 stability contract) and emits woff2/woff in one pass. FontForge was **not**
used. Node is build-time only (`package.json`, installed on demand by the Makefile);
the published assets stay plain files. Stroke outlining and the masked-icon
show − hide resolution (§4) are done with Inkscape actions in `generate-font.sh`;
codepoints are allocated and the CSS emitted with bash + `jq`.

## 8. Scope & phasing

Outlining quality and font bloat vary by variant. Phase to de-risk:

- **Phase 1 (covers the Pivotick driver) — ✅ done:** `attributes`,
  `objects-framed`, `simple`, `hexagone`. These are the sets a graph consumer
  needs, and they outline cleanly (solid strokes, self-contained framed shapes).
- **Phase 2 — ✅ done (2026-07-02):** `objects`, `galaxies`. Both are cropped to a
  **non-square content box** (unlike the square Phase 1 sets), so `generate-font.sh`
  first scales + centres each glyph onto a square 24-unit em (`square_pad()`),
  reproducing the mask's `mask-size: contain`/centre. Galaxies are already filled
  Font Awesome art (no strokes/masks); plain `objects` reuse the same masked-icon
  show − hide path as `objects-framed`. Implementing this surfaced (and fixed) a
  latent Phase 1 bug: 4 icons (`android-app`, `android-permission`, `c2-list`,
  `crypto-material`) carry an invisible `fill="none"` padding rectangle that
  `path-union` merged over the whole glyph, so they shipped as solid squares in
  both `objects` and `objects-framed`. `outline_icon()` now strips no-stroke
  `fill="none"` paths before outlining.
- **Phase 3 / evaluate:** `galaxies-orbit` — the dashed orbital ring outlines into
  many tiny contours (§4). Assess font-size legibility and byte cost before
  including; may be intentionally excluded from the font (masks remain available
  for it regardless).

Whatever is excluded from a phase must be **logged explicitly** by
`generate-font.sh` (which variants/icons were skipped and why) so a missing glyph
never reads as "silently covered."

## 9. Acceptance criteria

1. `make font` produces `exports/font/misp-iconify.{woff2,woff}` and
   `exports/font/icons-font.css`.
2. A page loading **only** `icons-font.css` renders
   `<span class="misp-icon misp-icon-domain misp-attributes"></span>` as the domain
   glyph, tintable via `color`, scalable via `font-size`.
3. Every in-scope stroked source icon (verify with `domain`, which is fully
   stroked) renders as a **filled** glyph — not blank, not a hollow outline.
4. Codepoints are stable: running `make font` twice, and after adding one new
   icon, leaves all previously-assigned codepoints unchanged;
   `metadata/codepoints.json` only grows.
5. `icons.css` (mask) output is byte-for-byte unchanged by this feature.
6. **Pivotick end-to-end:** the MISP Pivot Explorer, switched to load
   `icons-font.css` and use Pivotick's `iconClass`/`iconUnicode` hook, renders the
   correct per-node glyph with **no `<foreignObject>`**.

## 10. Consumer example — Pivotick after this ships

Today (mask set → must use the `html`/foreignObject hook):

```js
defaultNodeStyle: {
  html: (node) => {
    const span = document.createElement('span');
    span.className = 'misp-icon misp-icon-domain misp-attributes';
    return span;                    // wrapped in a <foreignObject> per node
  }
}
```

With the webfont (native text path, no foreignObject):

```js
defaultNodeStyle: {
  // Pivotick reads --fa off the class via faGlyph(); the font renders it as <text>.
  iconClass: (node) => 'misp-icon ' + iconClassesForData(node.getData())
}
```

## 11. Open questions / decisions needed

All resolved for Phase 1:

- **D-1 — Class collision strategy.** ✅ **Identical class names + mutually-exclusive
  stylesheets** (§5.6). Consumer markup is portable; a consumer loads exactly one of
  `icons.css` (mask) or `icons-font.css` (font).
- **D-2 — Where `font` runs in CI.** ✅ `font` is folded into `make all` and reached
  in `generate-assets.yml` via a dedicated `make font` step; the workflow now sets up
  Node + `npm ci` (not FontForge) and commits `exports/` + `metadata/codepoints.json`.
- **D-3 — `--fa` alias.** ✅ **Neutral `--misp-icon` only — no `--fa` alias.** The
  library is deliberately not coupled to FontAwesome naming. Consequence: Pivotick's
  `faGlyph()` needs a small upstream change to read `--misp-icon` (README documents
  the exact JS decode). Tracked as upstream Pivotick work, not a blocker here.
- **D-4 — galaxies-orbit inclusion.** ✅ **Excluded** from Phase 1 (Phase 3, still to
  evaluate). Masks remain available for it.
- **D-5 — Ligatures.** ✅ **Deferred** to a future version.

## 12. Risks

- **Outlining fidelity.** Round caps/joins and thin strokes can distort when
  outlined + unioned; needs visual QA per variant (the catalog/README render is a
  good diffing surface).
- **Codepoint drift.** The single most damaging failure mode for consumers;
  mitigated by the checked-in map + hard-fail on reassignment (§5.1, AC-4).
- **Toolchain creep.** `fantasticon` adds a build-only Node dependency to a
  previously Node-free repo (accepted, §7). It is dev/CI-only; consumers still get
  plain files.
- **Two sources of truth.** Mask and font must stay in sync as icons are
  added/removed; both are regenerated from the same `src/svg/**` by `make all`, so
  a full rebuild keeps them aligned.
